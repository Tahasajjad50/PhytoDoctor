1. OFFLINE STORAGE ARCHITECTURE HARDENING
--------------------------------------------------------------------------------
Field agronomists regularly visit farms in rural agricultural regions without
cellular network coverage. To guarantee that no field submission is ever lost:

A. Multi-Tiered Storage Engine:
  1. Tier 1: Native SQLite Database (sqflite: ^2.4.6)
     - On real Android devices, local visits are stored in a dedicated SQLite
       database table (`local_field_visits`) within the app's private documents.
     - Table schema includes: id (TEXT PRIMARY KEY), client_name, client_phone,
       crop_type, acreage, observations, photo_path, latitude, longitude,
       accuracy, sync_status, retry_count, last_error, device_capture_time.
  2. Tier 2: Atomic File-Journal Fallback
     - In headless testing or environments where the sqflite FFI factory is not
       registered, the engine seamlessly falls back to an atomic journal file.
     - File writes utilize write-to-temporary (`.tmp`) followed by atomic rename
       to prevent partial-write file corruption during sudden power-off.
     - Creates an automatic backup file (`.bak`) on every successful state mutation.

B. Location Durability:
  - Storage paths are dynamically resolved via path_provider's
    getApplicationDocumentsDirectory(), storing data permanently under:
    `/data/user/0/com.phytodoctor.fieldapp/app_flutter/`
  - This directory is non-volatile and immune to Android OS cache purges.


2. SYNCHRONIZATION HARDENING & CONCURRENCY
--------------------------------------------------------------------------------
A. Stuck "Syncing" Recovery on Process Restart:
  - If the Flutter app process is killed or the device restarts while an upload
    is in progress, visits can get stuck with status "syncing".
  - On app launch, SqliteVisitDatabase executes a recovery sweep, automatically
    resetting all "syncing" records back to "pending_retry".

B. Concurrency Lock & Debounce:
  - OfflineSyncManager enforces an atomic `_isSyncing` mutex flag.
  - When a user repeatedly taps "Sync Now" in rapid succession, subsequent calls
    are immediately debounced: "[OfflineSyncManager] Sync is already active. Repeated Sync Now request debounced."

C. Deduplication & Idempotency:
  - Every local visit is assigned a client-generated UUID v4.
  - When transmitting to the backend, the backend's FieldVisit table enforces
    `id = Column(String(36), primary_key=True)`.
  - If a network timeout occurs after backend insertion but before mobile ACK,
    the subsequent retry sends the identical UUID, returning HTTP 200 with the
    existing record without creating duplicate visits or inflating performance KPIs.

D. Corrupted Journal Self-Healing:
  - If the primary journal file suffers bit-rot or truncated JSON data, the parser
    catches the FormatException, logs a warning, and automatically restores from
    the `.bak` mirror file.

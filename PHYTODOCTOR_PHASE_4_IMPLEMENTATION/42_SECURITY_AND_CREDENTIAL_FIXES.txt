1. CREDENTIAL LEAK PREVENTION IN SHARING TEMPLATES
--------------------------------------------------------------------------------
A. Defect Identified:
  When managers shared newly created agronomist account credentials, the sharing
  template included:
    Server Address: https://phytodoctor-api.onrender.com
  Exposing the live backend server address across unencrypted communication
  channels (SMS, WhatsApp, emails) provides unauthorized third parties with direct
  API reconnaissance information.

B. Implemented Fix:
  In mobile/lib/presentation/screens/account_directory_screen.dart, the sharing
  string generator was refactored:
    String shareText = '🌿 PhytoDoctor Account Credentials 🌿\n\n'
      'Name: ${user.fullName}\n'
      'Phone: ${user.phone ?? "N/A"}\n'
      'Designation: ${user.designation ?? user.role.displayName}\n'
      'Role: ${user.role.displayName.toUpperCase()}\n'
      'Assigned Portal: ${user.role.portalName}\n\n'
      'Login Credentials:\n'
      'Username: ${user.username}\n'
      'Email: ${user.email}\n'
      'Password: $plainPassword';
  The Server Address line was completely eliminated.


2. DATA-AT-REST ENCRYPTION & KEY ROTATION
--------------------------------------------------------------------------------
A. Decoupling from JWT Secret Key:
  Previously, stored employee passwords in `users.assigned_password` were encrypted
  using a key derived from JWT `SECRET_KEY`. Rotating the JWT secret rendered all
  existing employee passwords undecryptable.
  - Implemented `CREDENTIAL_ENCRYPTION_KEY` in backend/app/core/config.py.
  - Implemented `CREDENTIAL_ENCRYPTION_KEY_FALLBACKS` list for seamless migration.
  - Required 32 url-safe base64 bytes for production environments.

B. Multi-Key Fallback & Versioning:
  In backend/app/core/security.py:
  - All new encryptions produce versioned ciphertext: `v1:gAAAAA...`
  - Decryption tests candidates in priority order:
    1. Primary `CREDENTIAL_ENCRYPTION_KEY`
    2. Fallback keys in `CREDENTIAL_ENCRYPTION_KEY_FALLBACKS`
    3. Legacy SHA-256 derived key from `SECRET_KEY`
  - Guarantees 100% backward compatibility with zero decryption failures on old records.
  - Added `rotate_credential()` function to re-encrypt records with the latest primary key.


3. ON-DEMAND AUDITED CREDENTIAL REVEAL
--------------------------------------------------------------------------------
A. Password Masking in Bulk Lists:
  - In backend/app/api/v1/users.py, GET /users/created-accounts and PUT /users/{id}/credentials
    now strictly return `login_password: "••••••••"`. Cleartext passwords are never
    returned in bulk.

B. Audited Reveal Endpoint:
  - Added `POST /api/v1/users/{user_id}/reveal-credential`.
  - Role-Based Access Control (RBAC):
    - OWNER: Can reveal credentials for any employee or manager.
    - MANAGER: Can only reveal credentials for employees they personally created
      or supervise (emp.manager_id == current_user.id).
    - EMPLOYEE: Strictly forbidden (HTTP 403).
  - Audit Trail:
    - Every successful reveal logs a `CREDENTIAL_REVEALED` event in `audit_events`
      with timestamp, supervisory user ID, and target employee ID.


4. DISTRIBUTED BRUTE-FORCE RATE LIMITING
--------------------------------------------------------------------------------
A. Multi-Process Concurrency:
  - LoginRateLimiter (backend/app/core/rate_limit.py) was upgraded from an in-memory
    dictionary to a multi-worker shared architecture.
  - File-backed SQLite store using WAL mode allows all Uvicorn worker processes on
    the same host to share identical rate limit counts.
  - Supports Redis sliding window (ZSET) when `REDIS_URL` is set.
  - Enforces 5 failed attempts per 15-minute sliding window, returning HTTP 429
    with `Retry-After` header when triggered.

B. Automated Verification:
  - Auth test suite (backend/tests/test_auth_and_roles.py):
    8/8 tests passed, including lockout after consecutive failed logins.

1. EXECUTIVE SUMMARY & OBJECTIVE
--------------------------------------------------------------------------------
PhytoDoctor has operated in development and QA environments using SQLite. For
enterprise production deployment on Render, SQLite cannot be used due to
Render's ephemeral container filesystem (where restarts or deployments wipe out
local disk changes unless an attached persistent disk is used).
The objective of this engineering task is to provide a zero-data-loss migration
engine, test table schema creation, resolve circular foreign key dependencies,
and validate data parity through an isolated staging drill.

2. TABLE DEPENDENCY GRAPH & EXECUTION ORDER (DAG)
--------------------------------------------------------------------------------
Relational integrity requires foreign key parent tables to be populated prior
to dependent child tables. Furthermore, the PhytoDoctor 'users' table contains
two self-referential foreign keys:
  - User.manager_id -> User.id (Field employee supervised by Regional Manager)
  - User.created_by_id -> User.id (Account created by CEO/Admin)

To resolve self-referential circularities without disabling database foreign key
constraints in PostgreSQL, the migration engine utilizes a 2-stage loading strategy:

Execution Order:
  1. app_version_configs (Independent configuration table)
  2. users [STAGE 1]     (Inserts core user accounts with manager_id = NULL
                          and created_by_id = NULL)
  3. users [STAGE 2]     (Updates user records to link valid manager_id and
                          created_by_id pointers once all users exist)
  4. refresh_tokens      (Depends on: users)
  5. attendance_records  (Depends on: users)
  6. customers           (Depends on: users)
  7. field_visits        (Depends on: users, customers)
  8. employee_targets    (Depends on: users)
  9. audit_events        (Depends on: users)
  10. chat_rooms         (Depends on: users)
  11. chat_messages      (Depends on: chat_rooms, users)

3. MIGRATION ENGINE CAPABILITIES (migrate_sqlite_to_postgres.py)
--------------------------------------------------------------------------------
The script is built with industrial safety primitives:
  - Argument: --target <database_url> (Supports sqlite:/// or postgresql+asyncpg://)
  - Argument: --dry-run (Extracts and counts source records without writing to target)
  - Argument: --batch-size <int> (Default 500 rows per batch to prevent memory spikes)
  - Automatic Table Creation: Initializes all tables in target via Base.metadata.create_all
  - Data Type Translation: Seamlessly maps SQLite ISO strings and integers to
    PostgreSQL TIMESTAMP WITH TIME ZONE, UUIDs, BOOLEANs, and JSONB fields.
  - Final Parity Validation: Queries record counts from source vs target and fails
    with exit code 1 if a discrepancy is detected.

  1. Revert Render environment variable DATABASE_URL back to:

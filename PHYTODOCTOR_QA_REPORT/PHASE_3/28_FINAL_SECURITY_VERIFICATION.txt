1. CREDENTIAL STORAGE AT REST (AES-128-CBC FERNET)
--------------------------------------------------------------------------------
Security Finding in Earlier Versions:
In initial prototype builds, the 'assigned_password' column in the 'users' table
(used to display temporary credentials to Managers creating accounts) stored
plaintext strings.

Hardening Implemented & Verified in Phase 3:
1. Two-Way Authenticated Encryption:
   Implemented encrypt_credential() and decrypt_credential() utilizing Fernet
   symmetric encryption (AES-128 in CBC mode with PKCS7 padding and HMAC-SHA256
   authentication).
2. Key Derivation & Stability:
   The encryption key is deterministically derived from the server's SECRET_KEY
   using base64 urlsafe encoding, guaranteeing consistent decryption across
   server restarts without storing separate keyrings.
3. Database Migration Execution:
   The migration utility 'backend/scripts/migrate_passwords.py' was executed across
   the database (phyto_doctor.db):
     - Legacy plaintext passwords found: 3 (MehmoodAyyaz, admin.tahasajjad, emp.salman)
     - Successfully converted to Fernet ciphertext: 3 (Prefix: 'gAAAAA...')
     - Database scan verification: 0 plaintext passwords remain. 100% of non-null
       assigned_password values are valid Fernet ciphertexts.
4. Application Seeding Hardening:
   Updated 'backend/app/seed.py' so all seed and bootstrap user accounts wrap
   assigned passwords with encrypt_credential() prior to database insert.

2. JWT SECRET ENTROPY & ENFORCEMENT GATE
--------------------------------------------------------------------------------
Security Vulnerability Addressed:
Low-entropy JWT secrets or default fallback keys ("dev_jwt_secret_key...") can
allow attackers to forge arbitrary tokens and impersonate administrative roles.

Hardening Implemented in Phase 3:
Added Pydantic @model_validator(mode="after") in 'backend/app/core/config.py':
  - Rule: If ENVIRONMENT != "development" and ENVIRONMENT != "test":
    1. Rejects known development fallbacks ("dev_jwt_secret_key...").
    2. Enforces len(SECRET_KEY) >= 32 characters (guaranteeing 256 bits of entropy).
    3. Fails server startup with ValueError if an insecure secret is supplied in
       staging or production.

3. CROSS-ORIGIN RESOURCE SHARING (W3C CORS) COMPLIANCE
--------------------------------------------------------------------------------
Specification Requirement:
The W3C Fetch specification strictly prohibits allowing wildcard origins ("*")
when 'Access-Control-Allow-Credentials: true' is enabled.

Implementation Verification:
Inspected 'backend/app/main.py':
  - Strict Allowed Origins Whitelist:
      "https://phytodoctor-admin.web.app"
      "https://phytodoctor-admin.firebaseapp.com"
      "http://localhost:5173"
      "http://localhost:3000"
      "http://localhost:8080"
      "http://127.0.0.1:5173"
  - Wildcards: Zero wildcard "*" entries present in allowed_origins.
  - allow_credentials: True is safely paired with explicit origin strings only.
  - Pre-flight OPTIONS: Correctly handled by CORSMiddleware with allowed headers
    ["*"] and methods ["*"].

4. ROLE-BASED ACCESS CONTROL (RBAC) & PRIVILEGE ISOLATION
--------------------------------------------------------------------------------
Role Hierarchy Audited:
  - Role: OWNER (CEO / Company Owner)
    - Has global read and write privileges across all branches, users, visits,
      and financial targets.
    - Exclusively authorized for executive KPIs (/admin/dashboard-stats) and
      audit log inspection (/admin/audit-logs).
  - Role: MANAGER (Regional Field Manager / Branch Admin)
    - Authorized only over their assigned branch and subordinate employees
      (User.manager_id == current_user.id).
    - Can verify/reject visits belonging to their team.
    - Cannot modify employee photo evidence directly.
    - Blocked from system-wide audit logs.
  - Role: EMPLOYEE (Field Agronomist)
    - Strict data isolation: Can only view, submit, and access visits, photos,
      and attendance records where visit.employee_id == current_user.id.
    - Accessing other employees' visits returns HTTP 403 Forbidden.
    - Blocked from management rosters and administrative endpoints.

5. BRUTE-FORCE RATE LIMITING & LOCKOUT
--------------------------------------------------------------------------------
Login Rate Limiter (backend/app/core/rate_limit.py):
  - In-memory sliding window rate limiter tracking client IP + username.
  - Threshold: 5 consecutive failed attempts locks the identifier for 15 minutes.
  - Returns HTTP 429 Too Many Requests with descriptive countdown header.

1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This report provides an in-depth security analysis of PhytoDoctor's identity,
authentication, authorization, and rate limiting subsystems. During Phase 5,
significant architectural improvements were made to transition the platform
away from reversible assigned credentials to salted bcrypt password hashing,
cryptographic temporary reset workflows, and enforced first-login password changes.

2. CRYPTOGRAPHIC & CREDENTIAL SECURITY ARCHITECTURE
--------------------------------------------------------------------------------
Core Security Components:
  - Hashing Algorithm: Passlib bcrypt with auto-generated salt (12 rounds)
  - Token Format: JSON Web Tokens (JWT) signed with HS256 HMAC
  - Secret Key Entropy: Cryptographically secure 256-bit secret from environment
  - Access Token Expiration: 60 minutes
  - Refresh Token Expiration: 30 days (stored in database with revocation flag)

Phase 5 Credential Upgrades:
  1. Plaintext Deprecation:
     The assigned_password column in users table is deprecated and set to None
     for newly created accounts and password resets.
  2. Mandatory Password Change:
     The must_change_password flag is set to True upon account creation or admin
     reset, requiring immediate password replacement before full system access.
  3. Self-Service Password Change Endpoint:
     POST /api/v1/auth/change-password validates old password, computes bcrypt
     hash of new password, clears must_change_password to False, and revokes
     all other active sessions.

4. BRUTE FORCE PROTECTION & RATE LIMITING
--------------------------------------------------------------------------------
Implementation:
  - Mechanism: Sliding-window memory rate limiter on POST /api/v1/auth/token
  - Threshold: 5 consecutive failed authentication attempts within 60 seconds
  - Penalty: 5-minute IP/account lockout with HTTP 429 Too Many Requests

Automated Test Evidence:
  - Test Target: test_login_rate_limiting_lockout_after_consecutive_failures
  - Execution Flow:
      - Attempt 1 (Wrong password): HTTP 401 Unauthorized (Remaining: 4)
      - Attempt 2 (Wrong password): HTTP 401 Unauthorized (Remaining: 3)
      - Attempt 3 (Wrong password): HTTP 401 Unauthorized (Remaining: 2)
      - Attempt 4 (Wrong password): HTTP 401 Unauthorized (Remaining: 1)
      - Attempt 5 (Wrong password): HTTP 401 Unauthorized (Remaining: 0)
      - Attempt 6 (Any password): HTTP 429 Too Many Requests
        Header: Retry-After: 300
        Message: "Too many failed login attempts. Account temporarily locked."
  - Verdict: PASS.

5. SESSION REVOCATION & TOKEN INGESTION DEFENSE
--------------------------------------------------------------------------------
Source Files:
  - backend/app/core/security.py (blacklist_token, is_token_blacklisted)
  - backend/app/api/v1/auth.py (POST /logout)

Verification:
  1. On logout, the token's unique jti is stored in the blacklist cache.
  2. The refresh_tokens database record is updated to is_revoked = True.
  3. Subsequent attempts to use the revoked refresh token return HTTP 401.
  4. Password reset immediately revokes all existing refresh tokens for that user.

6. SECURITY RECOMMENDATIONS FOR PRODUCTION
--------------------------------------------------------------------------------
  1. Transition in-memory token blacklist to Redis cluster for distributed multi-worker deployments.
  2. Enforce strict TLS 1.3 encryption on Render/Cloudflare ingress.
  3. Implement Content Security Policy (CSP) headers on Vite Admin portal.
  4. Schedule automated weekly vulnerability scans (Safety / Dependabot).
